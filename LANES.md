## Component contract

- Image/PDF libraries expose CPU RGBA8 pixel bytes with explicit width/height and useful document metadata/errors. Do not depend on egui, tab IDs, textures, or each other's private types; the integration owner supplies the small UI adapters and shared total-cache budget.
- Create/rename is a synchronous backend invoked later by the window-level operation worker. Preserve native paths, fixed source identity, no-overwrite semantics and clear partial/failure outcomes. No copy/move/delete engine or GUI is hidden in this lane.
- Each component is a small standalone Rust library manifest under its owned directory, with focused checks runnable via cargo --manifest-path. Root Taskfile/Cargo already belong to the application; component build output stays under the worktree's ignored root target directory. Keep optional component documentation local.
- Existing source/spec/AGENTS are read-only discovery context. No root dependency/lockfile edits, README/tracker edits, speculative framework, or sibling component changes by lane writers.
- Tests only create/remove owned disposable fixtures. Native/provider-dependent evidence remains explicitly pending when unavailable; never claim a probe passed because it was skipped.

## Scheduling and promotion policy

Use a rolling pipeline, not synchronized rounds. Start three independent feature slices; replenish prepared feature slots on completion while read-only review and serial integration continue. Reserve up to two slots for fresh workers correcting failed reviews. A review gates its candidate and dependent slices, not unrelated implementation. At three ready candidates awaiting integration, prioritize integration over new dispatch; blocked candidates do not occupy ready capacity. Never invent work or bypass a decision/safety gate. Freeze each candidate head, baseline, owned paths and check evidence before review. Persist handoffs in tracked lane-local documents or root handoff/, never only in target/. Reconcile live ownership and durable heads after interruption before relaunch. Repeated supervisor provider failures halt new dispatch; workers may finish their bounded commissions but never approve or integrate themselves.

2. A lane returns its branch/head, allowed changed paths, exact checks, native/license limits and managed handoff. Keep its worktree and branch until review and promotion are complete.
3. Fresh read-only review inspects that exact candidate, focusing on concrete contract/safety failures. Filesystem safety blockers prevent promotion/enablement; speculative/style issues do not become gates.
4. Parent promotes one reviewed component at a time using the rebase/squash policy below. Shared manifest/UI changes are integration-owned, not parallel-writer-owned. The original review does not approve changed conflict resolutions or adapters; independently review safety-relevant integration changes and run affected checks on the resulting candidate.

For integration, explicitly approved history policy is rebase plus squash: only after a lane is terminal, clean and accepted, preserve its reviewed head in a local reference, rebase onto accepted main, squash its component commits into one meaningful commit, verify the resulting patch and fast-forward main. Never rebase an active writer or rewrite accepted main. Keep original review evidence linked to the preserved head.
6. Run formatting/incremental compile and affected tests for the integration. Full suite and a native smoke happen at the corresponding checkpoint, not after every component edit.
7. Backend-only completion does not mark the entire GUI feature implemented. Record remaining UI/cache/queue/packaging clauses in PROGRESS.md. Do not silently shrink the spec.
8. No force pushes, destructive resets, accepted-main history rewriting or automatic worktree cleanup. Completed owned lanes may undergo only the explicitly approved rebase/squash integration above. Remove an owned worktree only when terminal, clean, durably promoted and no later check needs it; retain local branches until explicitly cleared.

If a component is blocked, preserve its partial work and name the next decision/action; independent lanes continue. Keep the shared board current at supervisor boundaries. Native Pi remains the execution protocol; no silent CLI/model fallback.
