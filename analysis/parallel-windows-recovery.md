## Clipboard read, write and command handoff

CR zeroes its 64-byte output, opens `OpenClipboard(NULL)`, and returns the zero output on failure. Input mask `1` requests text; mask `2` requests CF_HDROP. Successful opening ends with CloseClipboard.
CR prefers CF_UNICODETEXT `13`; only format unavailability permits CF_TEXT `1` fallback, not Unicode GetClipboardData/GlobalLock failure. It scans to NUL, converts Unicode through `0x140188d50`, or copies text bytes through `0x1401b8530`, then unlocks.
CR reads CF_HDROP `15` via GetClipboardData/GlobalLock, adds `DROPFILES.pFiles` to the locked base, and scans the double-NUL list itself. `fWide==0` stores borrowed byte spans; the wide branch converts strings into arena storage. It does not use DragQueryFileW, GlobalSize, or visible payload bounds validation.
CR unlocks the CF_HDROP handle before returning, so narrow-path records are not visibly copied into owned storage. After the file/text branch, it always registers and reads `Preferred DropEffect`; only DWORD exactly `2` sets the output's first DWORD to 1. Other values, including combined masks, are not interpreted as move.
CW calls OpenClipboard(NULL), EmptyClipboard, then optionally SetClipboardData for Unicode text `13`, files `15`, and `Preferred DropEffect`. The move marker allocates `GlobalAlloc(2,4)`, writes DWORD `2`, unlocks and submits. A zero marker does not publish a copy-effect DWORD. Each publication contributes to its success return; publication is not atomic. CloseClipboard is called even on open failure.
DF builds a `20`-byte DROPFILES header followed by UTF-16 path strings. It uses `GlobalAlloc(0x42,total+2)`, meaning GMEM_MOVEABLE|GMEM_ZEROINIT, and GlobalLock/Unlock. Header writes give `pFiles=20`, `pt={0,0}`, `fNC=1`, `fWide=1`. Zero initialization supplies each path NUL and the extra list NUL. Conversion uses `0x140187f00`, then an explicit temporary terminator.
DF frees the HGLOBAL on lock failure and releases its temporary arena. Successful SetClipboardData transfers handle ownership by Windows contract. CW has no visible GlobalFree on SetClipboardData failure; its text-allocation helper `0x14018c6c0` remains uninspected. A Rust implementation should not copy that missing failure cleanup or unchecked external-data scanning.
CP and CT obtain selected items using `0x1400cfff0` with flags `0xc0` and `0x80`, respectively. With nonempty selection and phase argument `2`, both call `0x1400cdd40(...,3)` then CW; CT forces the first DWORD to `1`. The selection and clipboard-record builders remain uninspected. Both return whether selection was empty, not CW's success.
PA calls CR with files-only flag `2`, gates through `0x1400d06d0`, and at phase `2` builds a request for `0x1400c9cd0`, then calls `0x14004ba90`. Its request discriminator is usually the recovered move boolean, but becomes `2` when comparison against a global 16-byte value succeeds. Those discriminator semantics and operation outcomes are unresolved. Move-marked paste empties the clipboard after submitting the hooks, not after visibly verified completion.
ML's filename is misleading: its complete body initializes OpenGL renderer/shaders, not clipboard-change state. Do not use it to claim cut highlighting or clipboard notifications. WP's WM_CLIPBOARDUPDATE `0x31d` only sets `S+0x898=1`; listener installation and the consumer of that flag remain unresolved.

## Outgoing OLE drag and registration

DS obtains a shell IDataObject rather than constructing a demonstrated custom IDataObject. With no selected entries it calls `0x14019ef30`, then parent slot `+0x40`, matching IShellFolder::CreateViewObject with resolved IID_IShellView, then view `+0x78`, matching GetItemObject with selector `0` and IID_IDataObject.
With selected entries DS compares its source value to globals `S+0x1300/+0x1308`. Unequal uses SO; equal uses uninspected `0x1401a1be0`. The meaning of that special source is not established here. SO obtains a parent through `0x14019ef30`, parses child names via parent slot `+0x18`, and requests IID_IDataObject through `+0x50`, matching GetUIObjectOf. SO releases the parent and CoTaskMemFree-cleans successfully collected child PIDLs, including partial failure.
After successful acquisition DS sets outgoing-active state at its base `+0x58`, copies the source value to `+0x60/+0x68`, and calls `SHDoDragDrop(NULL,dataObject,NULL,7,&effect)`. Mask `7` allows copy|move|link; the null IDropSource delegates source behavior to the shell. The resulting effect is not consumed in this body. SHDoDragDrop supplies the shell's modal OLE drag loop by API contract; this is not observed runtime/message-loop evidence.
After the call DS logs HRESULT, releases IDataObject, clears outgoing-active state, and releases the temporary arena. The empty-selection path visibly releases its parent but not the created shell-view pointer. No custom drag image, cancellation policy, or source-side move deletion is recovered from DS.
RG calls RegisterDragDrop with HWND at base `+0x50` and interface at `+0x38`, then CoCreateInstance with CLSID_DragDropHelper, context `1`, IID_IDropTargetHelper, output `+0x48`. Creation failure revokes registration; success atomically increments `+0x40`. Normal teardown/revocation and interface QueryInterface/AddRef/Release bodies remain uninspected.

## Incoming data, target acquisition and effects

Use `S=DAT_1401e8b90` as the application-state pointer and `B=S+0x8a0` as the base passed to TA. EN retains IDataObject at `S+0x958` using AddRef, sets active `S+0x9a8`, and overwrites stored and caller effects with `7`, without intersecting the entering allowed mask.
EN records right-only button state with `(keys&3)==2`; EN/OV compact Shift, Control, Alt into bits `1,2,4`. EN installs `SetWindowsHookExW(14,0x140194fa0,NULL,0)` if needed, calls IR, then dispatches event `2` with a zeroed `0x1b8`-byte payload. Hook type 14 is WH_MOUSE_LL; the hook body is uninspected.
IR at `0x140194a2b` directly calls IDataObject::GetData with FORMATETC `{cfFormat=15,ptd=NULL,dwAspect=1,lindex=-1,tymed=1}`, meaning CF_HDROP/DVASPECT_CONTENT/TYMED_HGLOBAL. It does not first call QueryGetData. Negative HRESULT returns immediately.
On successful GetData, IR GlobalLock-locks the returned HGLOBAL, calls `DragQueryFileW(lockedValue,0xffffffff,NULL,0)` for count at `0x140194a82`, then reads each item into a fixed buffer with cch `0x104` at `0x140194c54`. It does not query each required length or retry long paths.
IR converts each result through `0x140188d50`, strips trailing '/' and '\\' without a visible root special case, and stores 16-byte records in the provided arena/array. It sets the DWORD at arena `+0x44` to `1`, unlocks at `0x140194ce0`, and ReleaseStgMedium-cleans at `0x140194cfb`, including lock failure. No DragFinish or caller-owned GlobalFree appears.
IR proves a CF_HDROP extraction path, not exclusive format acceptance by the whole application. GetData failure does not make EN return failure or reject effect `7`; delegated shell handling may still accept other formats. No FileGroupDescriptor/FileContents decoder is demonstrated in these inspected bodies.
OV dispatches event `3`, then reads payload selector and fields synchronously. Selector `1` keeps a cached target only while its associated 16-byte value compares equal; otherwise it calls DragLeave and Release. It caches the new key state, optionally changes left to right button when payload flag equals `1`, and calls TA.
TA's filename says effect picker, but its body acquires a shell target. It runs only if `B+0x80` is null, its selector argument is `1`, and the supplied path/value length is nonzero. During an outgoing drag, a target equal to the source suppresses acquisition unless Shift/Control bits `0x0c` or the remembered right-button flag are set. Alt alone does not bypass this gate.
TA converts and terminates the requested path, calls SHParseDisplayName at `0x140194e53`, SHBindToParent at `0x140194e85`, then parent `+0x50` at `0x140194ec9` with one child and resolved IID_IDropTarget. It releases the parent, frees the absolute PIDL, and releases temporary arena storage.
TA calls the acquired IDropTarget::DragEnter at `0x140194f0a` with stored IDataObject, keys, packed point, and effect initialized from `B+0x5c`. Failure releases the target; success caches it at `B+0x80` with a copied target value. Its DragEnter output effect is not visibly persisted. This is not a local copy/move/link precedence algorithm.
OV then calls cached target DragOver with effect initialized from `S+0x8fc`; nonnegative HRESULT admits the result, otherwise effect stays zero. Selector `2` instead returns exactly `payloadEffect&7` and updates DropDescription when cached description fields change. Other selectors return zero. A transition away from selector `2` clears its description.
DD allocates `0x414` zeroed movable bytes, writes DROPDESCRIPTION type `1/2` unchanged, maps input `3` to `4`, and maps other values to `0`. It converts two texts into 260-WCHAR fields, copying at most 259 units each. FORMATETC uses registered `DropDescription`, aspect `1`, index `-1`, tymed `1`; STGMEDIUM is HGLOBAL with null release owner. IDataObject::SetData(...,TRUE) transfers ownership on success; DD frees on failure. This controls drag feedback, not file transfer.
LV calls cached DragLeave/Release, helper DragLeave, unhooks, calls uninspected cleanup `0x140194940`, then dispatches event `4`. EN/OV use resolved helper DragEnter/DragOver with point addresses; no ScreenToClient appears in these callbacks or TA.
DP unhooks, sets `S+0x9ab=1`, calls helper DragLeave, then cached target Drop using the last OV-derived key state rather than current Drop keys. It admits effect only for nonnegative HRESULT, releases the target, writes effect, calls helper Drop, releases/clears stored IDataObject, and dispatches event `5`. It returns delegated HRESULT; no target gives HRESULT zero/effect zero. Selector-2 application transfer is not visible in DP.

## UI handoff and thread behavior

UI is an inline call, not an observed cross-thread queue. It queries GetFocus, clears transient input/list state, and recycles queued input nodes. For events `2..4`, held mouse states become release markers even with focus; for other events, focus controls that clearing.
For drag events `2..5`, UI calls `0x1401ad6e0`, stops if `S+0x48` is nonzero, calls `0x1401af0a0`, then `0x1401afbc0(S,event,payload)` at `0x1401a9fec` and `0x1401ad170(S,payload)` at `0x1401a9ff7`. These four bodies remain uninspected. The wrapper proves synchronous payload handoff but not hit-testing, payload field meanings, transfer dispatch, or the internal message-pump details.
UI event `1`, used by WP's BeginPaint/EndPaint branch, only invokes `0x1401afbc0` after common clearing. Event `0` can wait using `MsgWaitForMultipleObjectsEx(0,NULL,INFINITE,0x1cff,4)` at `0x1401a9f22`, corresponding to QS_ALLINPUT and MWMO_INPUTAVAILABLE, before invoking its helpers. Drag callbacks do not enter that event-0 wait branch.
WP messages `0x8001..0x8003` update a wake-generation field. `0x8005/0x8006` update wheel state only while incoming-active is set. Their posting sites remain unknown because the mouse hook/pump bodies were not inspected. WP's ScreenToClient belongs to WM_NCHITTEST, not evidence of OLE drop-point conversion.
TP calls OleInitialize(NULL) at `0x1401b12d7` on the threadpool callback thread and ignores its HRESULT. It LocalAlloc-allocates 200 zeroed bytes, installs TLS, initializes scratch fields, and invokes the job callback stored at context `+8` at `0x1401b133b`, passing context `+0x10` and a packed second argument.
TP cleans three scratch arenas through `0x140001a10`, LocalFree-cleans TLS storage, clears TLS, and calls CloseThreadpoolWork. It returns the context to a shared list using atomic ticket counters and a PAUSE spin loop, not a UI message.
TP ends with a tail jump at `0x1401b13d8` through `0x1401bf890`, resolved as CoUninitialize. Ghidra's displayed arguments and jumptable warning are not a valid CoUninitialize signature. The body does not show OleUninitialize, check apartment setup, or pump messages around arbitrary job callbacks. OC lists additional OleInitialize callers `0x140188fb0` and `0x1401b13e0`, neither inspected here. Proper Rust apartment initialization/cleanup is a reconstruction decision, not proof this worker is Explorer-compatible.
